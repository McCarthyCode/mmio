# Runbook: Broaden BotIdentity hook to cover all gh pr/issue subcommands

## What prompted this

Closing the stray duplicate PR #29 with `gh pr close 29 --comment "..."` posted the
comment under my own account (`McCarthyCode`) instead of `mmio-claude-agent[bot]`.
`.claude/hooks/BotIdentity.hook.sh` (introduced in #20) only special-cased three exact
`gh` subcommand forms — `gh pr create`, `gh pr comment`, `gh issue comment` — so `gh pr
close --comment` fell straight through unrewritten. The same gap applied to `gh pr
reopen -c`, `gh issue close -c`, `gh issue reopen -c`, and `gh pr review` (`-b`/`-c`/
`-r`) — any of these can post text attributed to whoever's authenticated.

Matt pointed at `AGENTS.md`'s existing wording — "Agent-authored commits and PRs are
meant to carry the `mmio-claude-agent[bot]` GitHub App identity instead" — and clarified
it's meant to cover comments too, not just commits and PR creation.

Separately: PR #29 itself only opened under my account in the first place because of a
second, more dangerous gap. The hook's multi-line/heredoc bailout silently skipped
rewriting *any* command containing an embedded newline. My `gh pr create` call was
chained in one shell invocation with a `cat > file <<'EOF' ... EOF` body-write, tripped
that bailout, and passed through completely unrewritten — with no warning at all.

## What changed

- **Blanket `gh pr`/`gh issue` routing.** Replaced the three-verb allowlist with a
  single regex match on `^gh[[:space:]]+(pr|issue)([[:space:]]|$)` — the leading `gh`
  token gets swapped for the full path to `scripts/gh_app_exec.sh` and every argument
  after it (subcommand, flags, everything) forwards unchanged. This covers every verb
  gh supports today (`close -c`, `reopen -c`, `review`, `edit`, `merge`, `create`,
  `comment`, ...) and any added later, without needing another hook edit per verb.
- **Loud heredoc/multiline bailout.** Previously `case "$CMD" in *$'\n'*|*'<<'*) exit 0
  ;; esac` — silent pass-through, no matter what was in the command. Now, if the
  command still looks like it contains a `git commit`/`gh pr`/`gh issue` statement
  (matched per-line, since `grep` already anchors `^`/`$` to each line of multi-line
  input by default), the hook denies the tool call with an explanation instead of
  guessing at a rewrite. This is a regex heuristic, not a real shell parser — biased
  toward over-blocking, since a false-positive just costs a retry as two plain
  commands, while a false negative reintroduces today's silent-wrong-identity bug.
- Updated `AGENTS.md` and `docs/runbooks/20.md` to describe the new coverage and the
  gaps that remain (see below).

## Verified before this PR was opened

Piped sample `PreToolUse` payloads directly to the hook:

```bash
echo '{"tool_input":{"command":"gh pr close 1 --comment \"x\""}}' | .claude/hooks/BotIdentity.hook.sh
echo '{"tool_input":{"command":"gh issue reopen 1 -c \"y\""}}' | .claude/hooks/BotIdentity.hook.sh
echo '{"tool_input":{"command":"gh pr review 1 -b \"z\" -c"}}' | .claude/hooks/BotIdentity.hook.sh
# => each rewrites `gh` to scripts/gh_app_exec.sh, rest of the args untouched

echo '{"tool_input":{"command":"git commit -m \"msg\""}}' | .claude/hooks/BotIdentity.hook.sh
echo '{"tool_input":{"command":"gh pr create --title t --body b"}}' | .claude/hooks/BotIdentity.hook.sh
# => unchanged rewrite behavior, no regression
```

And for the heredoc bailout (using `jq -n --arg cmd "$CMD"` to build a payload with a
real embedded newline, since JSON can't have a literal newline inside a string
otherwise):

```bash
CMD=$'cat > /tmp/x << \'EOF\'\nhello\nEOF\ngh pr create --title t --body-file /tmp/x'
jq -n --arg cmd "$CMD" '{tool_input:{command:$cmd}}' | .claude/hooks/BotIdentity.hook.sh
# => denied, with an explanation

CMD2=$'cat > /tmp/x << \'EOF\'\nhello world\nEOF'
jq -n --arg cmd "$CMD2" '{tool_input:{command:$cmd}}' | .claude/hooks/BotIdentity.hook.sh
# => no output (allowed, unmodified) -- benign heredoc, no mutating call inside

CMD3=$'cat > /tmp/x << \'EOF\'\nplease run git commit later\nEOF'
jq -n --arg cmd "$CMD3" '{tool_input:{command:$cmd}}' | .claude/hooks/BotIdentity.hook.sh
# => no output (allowed, unmodified) -- "git commit" appears mid-sentence in the heredoc
#    BODY text, not as its own statement, so it correctly doesn't false-positive
```

This PR's commit and the PR itself were both bot-authored by hand (`-c user.name=/-c
user.email=` on the commit, `scripts/gh_app_exec.sh pr create` directly for the PR) —
same as PR #21/#30 earlier today. The `PreToolUse` hook did not auto-fire for plain
`git commit` in this session even before this change (confirmed by testing a bare `git
commit -m "test"` payload through the hook script directly, which rewrites correctly in
isolation, vs. an actual `git commit` issued as a live Bash tool call in-session, which
came back unrewritten). Root cause not yet identified — flagging as a new known
limitation below rather than blocking this PR on it, since manual `-c`/`gh_app_exec.sh`
application is a reliable fallback.

## Known gaps (unchanged from #20, still not fixed)

- Bare `gh api` calls that happen to POST a comment/PR directly bypass this hook
  entirely.
- A global flag before the subcommand (`gh -R owner/repo pr comment ...`) won't match
  the anchored regex.

## New known limitation: PreToolUse hook not firing this session

Confirmed today: piping a `PreToolUse` payload directly to
`.claude/hooks/BotIdentity.hook.sh` produces the correct rewrite, but an actual `git
commit` issued as a live Bash tool call in this same session came back authored as the
human, unrewritten — meaning the harness did not invoke the hook for that call at all
(not a hook-logic bug; the script itself is correct in isolation). This showed up
working from a git worktree created mid-session via the `EnterWorktree` tool, which may
be a relevant factor (project-scoped hooks are documented elsewhere as loading at
session start — see #20's "Known limitation" section for the analogous
create-and-verify-in-the-same-session gap). Needs a fresh-session repro to isolate:
does a plain `git commit` in this repo, in a brand-new session, on a normal (non-mid-
session-worktree) checkout, get rewritten automatically? If not, the hook registration
itself needs investigating, independent of anything in this PR's diff.
