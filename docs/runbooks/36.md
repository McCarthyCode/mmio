# Runbook: Deploy to DigitalOcean App Platform, retire nginx and docker-compose split

## What prompted this

Issue #35 (successor to #28, which was closed and re-filed verbatim as #33 purely to
re-author it under the `mmio-claude-agent[bot]` identity — neither #28 nor #33's actual
scope had been implemented) asked to move mmio's hosting off manual AWS/EC2 onto
DigitalOcean App Platform, consolidate the split `docker/compose.yml` +
`docker/compose.dev.yml`, and set up staging/production environments.

## What changed

- **nginx retired entirely.** mmio is a single Flask/Gunicorn service — there's no real
  need for an in-repo reverse proxy once the hosting platform can terminate TLS and
  route domains itself. DO App Platform does exactly that, so `nginx/conf.d/*.conf` and
  the `nginx` service in `docker/compose.yml` are gone. This also closes a real gap: the
  TLS certs those configs mounted (`nginx/ssl/*.crt/.key`) were never tracked in git,
  provisioned out-of-band on the old EC2 host.
- **`app.yaml`** (DO App Spec, repo root) — a `services:` entry building straight from
  the existing root `Dockerfile` via DO's GitHub integration (`deploy_on_push: true`),
  `http_port: 8080` matching the Dockerfile's `EXPOSE`, and production `envs:`
  (`ENVIRONMENT`, `APP_DEBUG`, `APP_WORKERS`, `LOG_LEVEL` — the same variable names
  `docker/.env/*/www.env` used, just relocated). `domains:` lists all 8 production
  domain entries (`mattmccarthy.io` as `PRIMARY`, the rest — `.net`, `.org`,
  `mccarthycode.com`, and each `www.` — as `ALIAS`). An `ingress.rules` block replicates
  nginx's exact current redirect behavior: `mattmccarthy.net`/`.org`/`mccarthycode.com`
  (+ their `www.`) 301 to `https://mattmccarthy.io`, since today's `nginx/conf.d/*.conf`
  does the same via `return 301`.
- **Root `docker-compose.yaml`** replaces the compose.yml/compose.dev.yml split — one
  file, local-dev-only now (builds the Dockerfile, bind-mounts `./app`, runs `flask run
  --debug` on `:8080`). Production no longer needs a compose variant at all: DO builds
  and runs the container itself from the same Dockerfile.
- **`docker/` deleted entirely** — `build-image.sh` and the GHCR multi-arch build/push
  flow it drove are no longer needed, since DO builds directly from source rather than
  pulling a pre-built image from a registry.
- **No GitHub Actions workflow added.** `.github/workflows/` was deleted in #34 for
  being unreliable; DO's native `deploy_on_push: true` git integration replaces what
  those workflows partially did, with nothing to maintain on the repo side.
- `docs/actions.md` → `docs/deployment.md` (rewritten for the new flow); `README.md`'s
  stack description, project-structure tree, and local-dev instructions updated to
  match.

## Explicitly deferred (not in this PR)

- **Staging.** Today's `nginx/conf.d/mattmccarthy.io.conf` actually included
  `stage.mattmccarthy.io` in the same `server_name` as production, pointing at the same
  container — there was never real staging isolation to begin with. Standing up an
  actually-isolated staging environment is left to a follow-up issue rather than bundled
  in here, per the scope confirmed for this pass.
- A DevOps test suite and a per-PR GitHub-Actions test-environment pipeline — both
  explicitly out of scope in #28/#35.
- **Actually provisioning the DO App and cutting DNS over.** This PR is code only. Real
  cloud provisioning (`doctl apps create --spec app.yaml`) and pointing production DNS
  for `mattmccarthy.io`/`.net`/`.org`/`mccarthycode.com` at the new app are real,
  hard-to-reverse, costs-money actions requiring separate explicit sign-off — tracked as
  the next step after this PR merges, not done here.

## Verified before this PR was opened

- `doctl apps spec validate app.yaml` — passes clean against DO's live App Spec schema.
  Confirmed real, supported fields directly against the validator rather than guessing
  from documentation alone (DO's own docs pages for `ingress.rules` matchers were
  incomplete/ambiguous on some details, e.g. whether `authority.exact` is a valid
  matcher — the validator confirmed it is).
- `docker build .` succeeds from the unmodified root `Dockerfile`. Ran the built image
  directly (`flask run --host=0.0.0.0 --port=8080 --debug`, matching the new
  `docker-compose.yaml`'s command) and confirmed `GET /` returns `200`.
- **Known sandbox limitation:** `docker compose up`'s bind mount (`./app:/app`) could
  not be exercised end-to-end in this session — the session's Docker CLI talks to a
  remote/NAS-hosted daemon (`docker context`'s `DOCKER_HOST` points at a Unix socket
  under `/mnt/var/run/docker.sock`), so this container's own filesystem paths aren't
  visible to that daemon for bind-mounting (`Bind mount failed: ... does not exist`).
  This is an artifact of the dev sandbox (docker-outside-of-docker), not a defect in
  `docker-compose.yaml` — the same compose file will bind-mount normally on a real
  workstation or in CI where the Docker CLI and daemon share a filesystem. Verified the
  underlying image/serving behavior directly instead (see above).

## Next step (needs explicit go-ahead, tracked separately from this PR)

1. Confirm the `doctl` token already configured in this environment actually has
   app-write scope (a read-only check — `doctl apps list` — already succeeds, but
   `doctl account get` 403s, so write access is unconfirmed).
2. `doctl apps create --spec app.yaml` to stand up the real DO App.
3. Point DNS for the 4 production domains at DO (CNAME/ALIAS per DO's instructions,
   or delegate to DO's nameservers) — this is the step that actually needs sign-off
   before touching production DNS, kept deliberately separate from merging this PR.
4. TLS issuance is automatic once DNS verifies (DO uses Let's Encrypt internally) — no
   manual cert files needed going forward.
