# Runbook: GitHub App bot identity for agent-authored commits/PRs

Mirrors the setup already running in `McCarthyCode/School-Shop-LA` (see that repo's
`docs/runbooks/5.md` and `docs/runbooks/11.md`) — same mechanism, ported to this repo
under its own App (`mmio-claude-agent`) and its own namespaced env vars.

## What this solves

1. Agent-authored commits and PRs previously landed under the human's own GitHub
   identity, with no visual distinction from anything he committed by hand.
2. Git identity only controls *commit* metadata, not *PR* authorship — `gh pr create`
   authenticates as whatever `gh auth status` has stored locally, so PR/comment
   attribution needs a separate mechanism from commit attribution.

## Dashboard steps (already done, 2026-07-29)

The App was registered at `github.com/settings/apps/mmio-claude-agent`, installed on
this repo, and a private key generated — App ID `4385091`, Installation ID
`149937142`. These, plus the private key path, are stored in the global
`~/.claude/.env` under an `MMIO_` prefix:

```
MMIO_GH_APP_ID=4385091
MMIO_GH_APP_INSTALLATION_ID=149937142
MMIO_GH_APP_PRIVATE_KEY_PATH=/home/matt/.github-secrets/mmio-claude-agent.2026-07-29.private-key.pem
```

The prefix exists because that same global file already holds a second App's
credentials (`schoolshopla-claude-agent`) under the unprefixed `GH_APP_*` names —
reusing those names here would silently collide, with whichever repo's session set
the env last winning for both.

## How it works

- **Commits:** `.claude/hooks/BotIdentity.hook.sh` is a project-scoped
  `PreToolUse`/`Bash` hook (registered in `.claude/settings.json`) that rewrites any
  `git commit` command the assistant issues into
  `git -c user.name="mmio-claude-agent[bot]" -c user.email="308820401+mmio-claude-agent[bot]@users.noreply.github.com" commit ...`
  — a one-off override scoped to that single invocation. It never touches any config
  file, so **the repo-local `user.name`/`user.email` must stay unset, always** — that's
  what lets it fall back to the human's own global identity by default.
- **PRs, issues, comments, and reviews:** the same hook rewrites any `gh pr <verb>` or
  `gh issue <verb>` command (blanket-matched on the `pr`/`issue` subcommand, not an
  allowlist of specific verbs — `create`, `comment`, `close -c`, `reopen -c`, `review`,
  `edit`, `merge`, etc. all qualify) into calls to `scripts/gh_app_exec.sh`, which mints
  a fresh GitHub App installation token (via `scripts/gh_app_token.ts`) and runs
  `GH_TOKEN=<token> gh <subcommand>` — since a PR/issue/comment's "posted by" is
  determined by which credential authenticates the API call, not by any embedded
  metadata, this is the only way to get bot-attributed PRs, issues, and comments.
  (Originally this only special-cased `gh pr create`/`gh pr comment`/`gh issue comment`;
  broadened to the blanket match after `gh pr close --comment` slipped a closing comment
  out under the human's account on #29 — see the runbook for the PR that widened this.)
- **Why this is safe by construction, not just by convention:** `!`-prefixed shell
  passthrough (and anything run from the human's own terminal) never becomes a
  `PreToolUse` event, so a hook on the `Bash` matcher structurally cannot see, let alone
  rewrite, anything the human runs himself.

## The bot-account-ID gotcha

The email above uses `308820401`, which is the bot account's own numeric user ID — not
the App ID (`4385091`). Using the App ID there silently fails: the commit pushes fine
but GitHub can't link it to any account, so it renders as a blank/generic author
instead of the `[bot]`-tagged one. Looked up once via:

```bash
gh api "users/mmio-claude-agent%5Bbot%5D" --jq '{login, id, type}'
```

(`%5Bbot%5D` is `[bot]`, URL-encoded.)

## Verified before this PR was opened

```bash
bun --no-env-file scripts/gh_app_token.ts
# => prints a fresh installation token, expiry logged to stderr

scripts/gh_app_exec.sh api /rate_limit --jq '.rate.limit'
# => 5000 (confirms the token authenticates against the GitHub API)

gh api repos/McCarthyCode/mmio/commits/worktree-mmio-bot-identity \
  --jq '{login: .author.login, type: .author.type}'
# => {"login": "mmio-claude-agent[bot]", "type": "Bot"}
```

This PR itself was opened via `scripts/gh_app_exec.sh pr create` —
`gh pr view 20 --json author` confirms `app/mmio-claude-agent` as the author.

Note: the bootstrap commit above was pushed over the normal SSH `origin` (tied to the
human's own key), not an HTTPS+token remote, and still resolved as bot-authored —
commit attribution is by verified author-email match, independent of what credential
pushed it. The installation-token dance is only actually required for API calls that
create/comment (PR creation, PR/issue comments), where "posted by" comes from the
authenticating credential.

## Known limitation — verify in a fresh session

Claude Code loads project-scoped hooks (`.claude/settings.json`) at session start.
`BotIdentity.hook.sh` was created *during* the session that also wrote this runbook, so
it could not self-verify — the bootstrap commit for this PR was authored by hand with
the same `-c` override the hook applies, not by the hook firing.

**The first real test needs to happen in a session that started after this hook
already existed on disk:**

```bash
# In a fresh Claude Code session, in this repo, on any branch:
git commit --allow-empty -m "test: confirm BotIdentity hook fires"
gh api repos/McCarthyCode/mmio/commits/<sha> --jq '{login: .author.login, type: .author.type}'
# expect: {"login": "mmio-claude-agent[bot]", "type": "Bot"}
```

If it still shows the human's identity, check (in order): the hook file is executable,
`jq` is on `PATH`, `$CLAUDE_PROJECT_DIR` resolves to the repo/worktree root, and the
hook isn't erroring silently (test by piping a sample `PreToolUse` payload to it
directly:
`echo '{"tool_input":{"command":"git commit -m x"}}' | .claude/hooks/BotIdentity.hook.sh`
— should print a JSON `updatedInput` block with the bot email in it).

## Known gaps

- **Bare `gh api` comment posting.** A bare `gh api` call that happens to POST a
  comment (e.g. directly to `/repos/.../issues/{n}/comments`) bypasses the blanket
  `gh pr`/`gh issue` match entirely — only those two subcommand forms are covered, not
  arbitrary `gh api` calls that happen to hit the same endpoints. Flagged here so it
  doesn't get rediscovered as a surprise later (same gap School-Shop-LA hit and
  documented in its own `docs/runbooks/11.md`).
- **Global flag before the subcommand.** `gh -R owner/repo pr comment ...` (repo flag
  ahead of `pr`/`issue`) won't match the hook's anchored regex, since it expects `gh`
  immediately followed by `pr`/`issue`.
- **Multi-line/heredoc commands are blocked, not rewritten.** If the assistant issues a
  `git commit`/`gh pr`/`gh issue` call chained together with a heredoc body-write in one
  shell invocation, the hook can't safely string-surgery it (see the PR that widened
  this hook's `gh` coverage for why) — it denies the call instead of guessing, and the
  assistant has to redo it as a separate body-write plus a plain single-line
  `git`/`gh` call using `-F`/`--body-file`.
